01｜使用方式與工作票欄位
本文件是開發工作票藍圖，不代表已在 GitHub 建立任何 Issue。正式開發時，每票至少包含：ID、標題、業務需求、依賴、優先級、交付範圍、驗收標準、測試案例、估時、負責人、狀態、PR／commit 與證據。未核准的政策應標示 BLOCKED，不得默認為既定。

11｜建議分批提交與審查方式
每個 PR 原則上對應一張工作票或一組高度相關的小票；Migration、API、測試、權限檢查必須在同一功能交付中完成。資料庫變更採向後相容優先，正式環境的破壞性 Migration 需有資料備份、回滾方案與人工核准。
依賴關係以本文件為工程排程基準，若發現循環依賴或跨模組未定義的欄位，先回寫 DOC-03／DOC-02，再調整工作票。不得為趕進度略過安全底座與交易完整性。
12｜正式開始開發的啟動門檻
①使用者明確授權開始開發；②確認 GitHub 專案及技術堆疊；③DEV-001～007 的設計與環境方案可行；④待決政策有安全的阻擋／停用策略；⑤每票具備可追溯驗收案例。未達條件時，工作票維持 Backlog。
交付聲明：本文件僅建立開發工作票規格，未建立 GitHub Issues、未執行測試、未修改 Supabase／Vercel。下一份 DOC-07 應定義部署、備份、監控、回滾及災難復原操作手冊。
