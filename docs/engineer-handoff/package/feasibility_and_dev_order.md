# 技術可行性與現況對照

評估對象：本 repo `cursor/engineering-mgmt-foundation-1c8f` 既有 MVP。  
結論：**可行**；建議以「規格收斂 → 安全資料層 → 現場作業 → 採購庫存財務 → 整合驗收」推進。

## 技術可行性

| 項目 | 評估 |
|---|---|
| 手機 PWA + 離線 | 可行；Vite PWA 已建，離線佇列／衝突仍待做 |
| Supabase Auth／DB／RLS | 可行；schema 草案有 org 隔離，正式 RLS 需每批 Migration 同步 |
| 採購額度／交易冪等 | 可行；本機已驗證門檻邏輯，正式需不可變額度事件＋交易鎖 |
| LINE 入口無推播 | 可行；與「系統內通知」策略一致 |
| RPO 1h／RTO 4h | 需在選定 Supabase／備份方案後做**實際還原演練**才可宣稱達標 |

## 建議開發順序（對齊 DOC-06／DOC-09）

1. **M0 收斂**：把 DOC-08／09 的 P0 修正寫進 schema／API 契約（報價↔維修 FK、額度事件、零用金、RLS）
2. **M1 安全基礎**：Email／密碼、organization membership、每表 RLS、稽核事件、備份演練門檻
3. **M2 現場作業**：班次模型完善、工地 session、回報／照片／缺失、離線冪等
4. **M3 材料財會**：庫存流水帳、移動加權平均過帳、報價版本、零用金、請款收款分離
5. **M4 維修保固統計**
6. **M5 整合測試與上線**（含 E2E-01～08）

## 工期特徵（技術面）

對話估算約「單一主要開發者 + AI、功能完整後再上線」量級偏大（多模組＋交易＋離線＋權限）。  
較實務的切法：先完成 **M1+M2 可內部试用**，但專案策略已選「主要功能完成後才正式使用」，因此正式上線應等 M3～M5 過關。

## 風險

1. ChatGPT sandbox 原檔無法下載 → 以此重建文件為準，若日後補上 Word／PDF 需再對 diff  
2. 規劃文件曾過度延伸 → 以最終整合規格 + DOC-08／09 為準，避免再開新 P0.x 階段  
3. 備份 RPO／RTO 不可只靠設定宣稱，需演練證據  

## 等待授權

在專案負責人明確同意「正式開發」前，建議只做規格對齊、可行性評估與既有示範維護，不視為上線開工。
