01｜目的與權限模型

05｜採購與零用金職責分離
一般採購：最終應付金額 ≥ NT$3,000 須事前核准。緊急採購：單次 ≤ NT$5,000，每人每日 ≤ NT$10,000（Asia/Taipei），需事由、授權及事後核對。超額不得藉拆單規避。
建議原則：申請人不可自行核准同筆一般採購；緊急採購事後核對人不得與購買人相同。小團隊如確需例外，須由 Owner 以明確政策授權並保留例外原因及完整稽核；此例外尚待核定。
零用金補充：申請→審核→撥款→確認收款，分別記錄操作人、時間、金額與憑證；核准不等於已撥款。

07｜RLS、API 與稽核安全契約
• 每筆有組織歸屬的資料，讀寫前均驗證 organization_id 與有效 membership；外鍵亦需檢查同組織。
• RLS 預設拒絕，僅授權策略可開放；Service Role 僅供可信後端使用，絕不可送至瀏覽器。
• API 必須重新驗證授權；不能相信前端送來的 role、organization_id、approved_by 或 cost_visibility。
• 權限異動、採購核准、退款、門禁存取、敏感匯出及資料刪除應記錄 audit_events；不得記錄明文密碼或完整門禁碼。
• audit_events 採不可變記錄，保留行為者、組織、資源、時間、動作、結果及必要的遮罩差異。
• Idempotency-Key 需綁定組織、使用者、操作與請求摘要；相同 key 不同內容回傳衝突。
• 對失敗登入、越權嘗試、批量匯出與異常頻率設定安全事件、速率限制及告警。

09｜未定案政策與實作前阻擋條件
尚待決定：採購申請人與核准人是否可在小團隊例外同人；管理者對敏感財務資料的預設可見性；個資保存期限及刪除／匿名化政策；敏感匯出審批機制；權限變更後快取失效時間。這些不可擅自標記為使用者已批准。
開發前須將權限字典、角色預設、API 操作及 RLS Policy 建立一對一映射；上線前需完成跨組織滲透測試、負面授權測試、金鑰掃描、備份還原演練及安全事件驗證。
